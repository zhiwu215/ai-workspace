# Repo Replay 输出模板与表现规范

本文档定义在执行 `repo-replay` 技能时的输出模板、排版格式与案例对照。

---

## 1. 痛点驱动三段式 (Pain-Driven Triad)

在讲解任何核心代码、设计模式或抽象分层时，必须使用如下格式结构进行剖析：

### 输出模板

````markdown
#### 模块/设计：[模块名称或设计点]

##### 1. 现实痛点 / 崩溃现场 (Pain Point)
[描述如果不引入此模块/抽象，在开发或线上会遇到的具体问题、竞态条件、代码难以维护的场景，或直接展示一段会翻车的朴素代码]

##### 2. 程序员当时的简易解法 (Naive Solution)
[展示最直觉但存在缺陷的初期写法，并简短分析其局限性]
```typescript
// 简易但不可持续的临时实现
```
> **局限性**：[一句话说明为什么这种写法不能直接用在生产/完整系统上]

##### 3. 演进抽离出的项目代码 (Evolved Code)
[展示当前项目实际采用的抽象设计、接口定义与整洁实现代码]
```typescript
// 最终演进后的生产代码
```
> **设计收益**：[说明本次演进带来了哪些解耦、可测性或扩展性收益]
````

## 2. Single-File Spike 模板

在跑通核心闭环前，先把代码集中在单个文件里。模板如下：

````markdown
#### Single-File Spike：`[核心场景名称]`

**目标**：用最脏的代码跑通 `[Tracer MVP 中的某个场景]`，并与原仓库的行为基线对比。

```typescript
// spike.ts
// 注意：这里允许全局变量、硬编码、if/else 嵌套，唯一目标是能跑通。
```

**验证命令**：
```bash
npx ts-node spike.ts
```

**原仓库行为基线输出**：
```
[来自原仓库示例/测试的输出]
```

**当前 spike 输出**：
```
[运行 spike 后的输出]
```

**结论**：[输出一致 / 还有哪些偏差，下一步如何收敛]
````

## 3. Evolution Backlog 模板

用于跟踪从原仓库拆解出的全部模块，并在 replay 过程中更新状态。

| 模块 / 功能 | 分类 | 状态 | 备注 |
| :--- | :--- | :--- | :--- |
| 核心调度算法 | Tracer | ✅ 已交付 | 在 Single-File Spike 中跑通 |
| HTTP API 适配 | Deferred | ⏳ 待挂载 | 核心稳定后接入 |
| JWT 鉴权中间件 | Deferred | ⏸️ 已放弃 | 本次只关注调度逻辑 |
| 前端管理界面 | Skipped | ⏸️ 已放弃 | 超出本次学习范围 |

分类说明：

- **Tracer**：核心闭环必须包含。
- **Deferred**：后续按增量挂载。
- **Skipped**：主动放弃，需记录原因。

## 4. 目录与命名动机解析规范 (Naming Intent)

在初始搭建目录骨架或新建模块文件时，使用结构化清单或表格向用户阐明命名依据：

### 命名动机表格范式

| 路径 / 文件名 | 命名动机与来源 | 承担职责与设计考虑 |
| :--- | :--- | :--- |
| `src/domain/` | **DDD 领域驱动设计约定** | 存放与框架无关的纯业务实体与核心计算逻辑，确保核心资产独立 |
| `src/adapters/` | **六边形架构 (Hexagonal) 约定** | 负责外部协议（HTTP、DB、MQ）与内部领域模型之间的转换适配 |
| `src/shared/pipeline.ts` | **项目专有语义** | 本项目核心是多阶段流式数据处理，以 `pipeline` 命名准确反映线性流水线特征 |

## 5. Diff Matrix 模板

任务收尾前，用此表对照当前实现与原仓库：

| 维度 | 当前实现 | 原仓库 | 差异类型 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| 核心调度算法 | 已实现 | 已实现 | 已对齐 | 行为基线测试通过 |
| 配置加载 | 硬编码对象 | YAML 配置文件 | 主动简化 | 为聚焦核心逻辑，暂不实现配置解析 |
| 持久化存储 | 内存 Map | SQLite | 主动放弃 | 本次不关注数据持久化 |
| 错误重试 | 未实现 | 指数退避 | 待补 | 属于Deferred，可后续挂载 |

差异类型：

- **已对齐**：行为一致。
- **主动简化**：核心行为一致，但实现更精简。
- **主动放弃**：功能未实现，已记录原因。
- **待补**：理论上应该补，尚未完成。

## 6. 正反教学案例对照

### 反模式 (Bad Pattern：事后总结视角 / 大全套代码轰炸)

- **现象**：一上来就贴出几十个文件、完整的 Web 路由、JWT 鉴权、数据库连接池、前端组件。
- **弊端**：学习者被海量外围胶水代码淹没，完全无法理解“核心业务到底是在解决什么问题”。

### 正模式 (Good Pattern：演进式增量推进)

- **第 1 步**：直接在单文件中实现核心业务算法或领域状态流转，用几行单元测试或控制台打印跑通最简输入输出闭环。
- **第 2 步**：暴露单文件由于状态膨胀带来的痛点（痛点三段式），引导重构为清晰的分层。
- **第 3 步**：在核心稳定后，再引入 HTTP 路由让外部可调用。
- **第 4 步**：最后作为增量模块挂载 JWT 鉴权与前端页面。
