请为当前仓库准备正式版，并在我审阅发布说明、确认版本号后发布 GitHub Release。若本次指定了发布平台，以指定平台为准。

1. 确认发布流程
   先阅读仓库的 AGENTS.md、发布文档、构建配置和 CI 工作流，并参考最近一次正式 Release，确认开发分支、发布分支、版本文件、变更日志、标签格式、构建方式及应发布的产物。遵循仓库已有约定。若关键信息缺失或冲突，只询问会影响本次发布的问题。

2. 起草发布说明，然后停下来
   在开发分支上，以当前发布系列的上一正式标签为基准，检查到当前开发分支为止的提交和实际差异。按仓库惯例编写 release-notes.md，重点写用户可感知的变化。若为首次发布，按首版内容起草。
   
   写完后告诉我文件位置和比较基准，停下来等我审阅和修改。此时不要修改版本号或变更日志，也不要提交、推送、打标签或创建 Release。

3. 根据审定内容准备版本
   只有在我明确回复「继续发布」并给出版本号后，才执行后续步骤。重新从磁盘读取 release-notes.md，以我审定的内容更新项目已有的变更日志，保留历史条目。按仓库约定更新版本号及需要同步的文件。
   
   在开发分支上只提交本次版本准备涉及的文件，使用仓库约定的提交格式。若无约定，使用 `chore(release): 发布v<版本号>`。随后推送开发分支。

4. 合并并验证发布产物
   获取远端最新状态，将开发分支合并到最新发布分支，优先快进合并。若仓库只有一个发布用分支，跳过合并。若要求通过 PR 合并，遵循该流程，以实际合并后的提交为准。
   
   记录发布提交的 SHA，按项目配置从该提交执行正式构建。逐项核对本次应发布的产物，包括文件名、版本、目标平台，以及更新清单中的文件引用、大小和校验值（如有）。避免误用旧构建留下的同名文件。若项目只能由标签触发正式构建，在打标签前向我说明实际顺序并等待确认。

5. 打标签并发布
   构建和核对通过后，确认发布分支当前 SHA 与已验证的发布提交一致。在该提交上按仓库约定创建标签，若无约定则使用轻量标签 `v<版本号>`。推送发布分支和该标签。若同名标签或 Release 已存在，停下来报告其状态，不覆盖。
   
   手动发布时，使用 `gh release create`，逐项传入已核对的实际产物路径，保留 `--verify-tag` 和 `--notes-file release-notes.md`，省略 `--title`。正文直接使用我审定的文件。若仓库已有自动发布工作流，让该工作流完成发布，核对正文和附件，避免重复创建 Release。
